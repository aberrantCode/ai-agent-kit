# Transcript data model

What a Claude Code session actually writes to disk, and the gotchas that will bite you
if you parse it naively.

## Layout

```
~/.claude/projects/<project-dir>/
├── <session-id>.jsonl                                  # main transcript, may be MISSING
└── <session-id>/
    └── subagents/
        ├── agent-<hash>.meta.json                       # direct Agent/Task dispatch
        ├── agent-<hash>.jsonl                            # that subagent's own transcript
        └── workflows/
            └── wf_<runid>/
                └── agent-<hash>.meta.json                # one per agent() call inside a Workflow run
```

`<project-dir>` encodes the working directory path with slashes/colons replaced by `-`
(e.g. `C--development-ac-repo-radar--worktrees-foo` for
`C:\development\ac-repo-radar\.worktrees\foo`).

## meta.json is ground truth for "was a subagent spawned"

Direct dispatch (`Agent`/`Task` tool):
```json
{"agentType":"general-purpose","description":"Author bulk-actions restoration plan","toolUseId":"toolu_01Gh...","spawnDepth":1,"model":"sonnet"}
```
`toolUseId` lets you correlate back to the exact `tool_use` block in the parent
`.jsonl` to recover the timestamp and the main-loop model at that turn.

Workflow-nested (`agent()` call inside a `Workflow` tool_use's script):
```json
{"agentType":"workflow-subagent","spawnDepth":1,"model":"haiku"}
```
No `toolUseId` -- these aren't individually addressable tool_use blocks in the parent,
they're generated by the Workflow runtime. Group by the `wf_<runid>` directory instead.

**`model` is absent, not `null` or `"unset"`, when the dispatch didn't specify one.**
That's the signal for "inherited the caller's model" -- always check with
`m.get("model", "unset")`, never assume the key exists.

**Nested delegation:** a subagent can itself dispatch further subagents. When it does,
its meta.json carries `parentAgentId` pointing at the hash of the dispatching agent, and
`spawnDepth` increments. This is how a chain of "search the logs" tasks can go 3 levels
deep before finally landing on the intended cheap model -- see the recursive
log-search finding in `references/report-template.md` for a worked example. Don't skip
checking `parentAgentId`; a flat count of models-by-task-description will miss that a
single top-level decision propagated downward unchanged.

## Two counting bugs to avoid

1. **`glob("<wf_dir>/**/*.meta.json", recursive=True)` matches top-level files too** --
   `**` can match zero directories, so a naive `glob(wf_dir + "/*.meta.json") +
   glob(wf_dir + "/**/*.meta.json", recursive=True)` counts every top-level file twice.
   Dedupe by resolved path, or just use the recursive glob alone (drop the non-recursive
   one).
2. **A session can fire the `Workflow` tool_use block more than once for the same run**
   (a `resumeFromRunId` continuation, or a "re-run this workflow" retry). If you attach
   the run's agent list to *every* `Workflow` tool_use block in the session instead of
   once per distinct `wf_<runid>`, you multiply the same 15 agents by however many times
   the workflow was invoked. Attribute a run's agents once, keyed by `wf_<runid>`, not by
   tool_use occurrence.

`scripts/mine_dispatches.py` already has both fixes applied and validated against a real
96-dispatch, 48-hour, 51-session window (the fixed run matched a hand-count exactly; the
buggy first draft inflated it to 190+). Use the script rather than re-deriving this from
scratch -- both bugs are easy to reintroduce and hard to notice, since the inflated
numbers still "look plausible."

## Sessions whose parent `.jsonl` cannot be found

Some sessions in a valid time window have subagent `meta.json` records under
`<session-id>/subagents/` but **no sibling `<session-id>.jsonl` at all**. This isn't
necessarily a bug -- it typically means the session is still open/concurrent and its
main transcript hasn't flushed yet, or the session was launched as a background/handoff
run whose top-level transcript lives under a different mechanism. When this happens:

- The dispatch is still real and countable -- meta.json alone gives you `model`,
  `agentType`, `spawnDepth`.
- You cannot independently recover the *main-loop* model for that dispatch from the
  transcript. Fall back to whatever the consuming prompt/skill/handoff document states
  about its own model pin (e.g. a `## Delegation` section that says "Main loop pinned to
  Opus"), and say explicitly in the report that this figure is attributed from the
  prompt's stated intent, not independently re-derived.
- Don't silently drop these records from the count just because one field is
  unavailable -- report `main_session_model: "unknown (parent jsonl not found)"` rather
  than fabricating a value.

## Path-translation trap (Windows + git-bash)

If you're running Python from a git-bash shell on Windows, `/c/Users/...`-style paths
work fine as separate argv (MSYS auto-translates them), but the **same string embedded
inside a `python -c` heredoc or literal is NOT translated** -- Python sees the literal
text and native Windows Python doesn't understand `/c/...`. Symptom: `glob()` silently
returns `[]` and `os.path.exists()` returns `False` for a path you can `ls` just fine
from bash. Fix: use `os.path.expanduser("~/.claude/projects")` inside the script (this
resolves correctly under native Windows Python regardless of the calling shell), or pass
paths in as CLI arguments rather than hardcoding them in inline `-c` code.
