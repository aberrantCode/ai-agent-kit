The One-Job Test

test an installed skill against one real job · keep / fork / delete · clean install ≠ good result

Why · installation proves nothing about quality
A skill that installs cleanly can still make the work worse. Every skill carries somebody's decisions — which tools to reach for, what counts as finished, what "good" looks like — and they arrive silently. This test surfaces those decisions and forces one verdict: keep, fork, or delete. Weight it heavily when the skill carries judgment (taste, business rules, a definition of done); lightly when it is narrow and mechanical from a trusted source.
seven steps, in order — do not skip step 2
The Seven Steps · same verbatim prompt, run twice
  • 1
    Name the one job
    One real task the user would do this week, with a real artifact. Specific enough that two people agree whether it came out well. Write the prompt down verbatim — the same string is used twice.
  • 2
    Write down what good looks like before running
    3–5 criteria in the user's words that could fail. "Looks professional" cannot fail; "palette outside the terracotta range" can. Record in criteria-worksheet.md — a criterion written after seeing output is a rationalization.
  • 3
    Read the skill and list its decisions
    Hunt for what it decides, not what it does. One line each — Decides: never asks before installing deps — flagged agrees / conflicts / unclear against step 2. A hard-coded conflict can end the test early.
  • 4
    Run the job without the skill — baseline
    Fresh session, same prompt, no skill. Save the artifact. Skipping this makes "the skill made it better" an unfalsifiable feeling.
  • 5
    Run the same job with the skill
    Same verbatim prompt, fresh session, skill available. Change nothing else — not the model, wording, or attachments. Save separately.
  • 6
    Score both against the step-2 criteria
    Artifacts side by side, pass/fail per criterion, into scorecard.csv. Never score a criterion the user did not write. Which criteria moved matters more than the tally.
  • 7
    Decide, then rerun
    Exactly one of three verdicts, with reasons — consult decision-card.md rather than eyeballing. A fork must be rerun at step 5 and rescored before it counts as fixed.
exactly one verdict
Keep
Won on criteria the user cares about and lost on none of the boundary ones. Nothing further to do.
Fork
Procedure is useful but the judgment is not the user's. Copy, rename (avoid update collisions), rewrite the conflicting decision lines — keep the mechanics, replace the taste — then rerun & rescore.
Delete
Lost, or won on nothing that matters, or conflicts a rewrite would not survive. A skill kept "just in case" still costs context — deletion is a real result.
What a crowded library costs
  • Adding a skill to fix bad output is the loop that produced the bad output.
  • Runtimes cap the visible skill list and trim it as it grows — past a dozen or two, skills compete and triggering gets unreliable.
  • Overlapping descriptions and conflicting instructions get averaged into duller work; no warning fires.
  • For an unexamined library, references/library-audit.md ranks which skills to one-job-test first.

Copy test-record-blank.md after the verdict; references/test-record-template.md explains each line with a worked example. One file per skill — so a folder named frontend-design-mine still explains itself later.
