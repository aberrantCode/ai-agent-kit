## F-OP-01 — No default merge-driver policy for generated/hook-regenerated docs causes systemic merge debt
- **Type**: missing-capability
- **Maps to**: init-repo (repo-init security/config provisioning) / merge sub-skill
- **Source**: `55b4f5b5-1488-4838-93fe-ea908b3425a7.jsonl` (session ~2026-07-15)
- **What happened**: User opened the session reporting "Merge debt — 7 PRs stalled 4-5 days," and diagnosed it themselves: "Six are conflicted, and the cause is self-inflicted: docs/STATUS.md is a generated file that's committed and hook-regenerated — 75 commits in two weeks, so any two branches collide. Same for append-only progress.md and the diagrams." The assistant then had to spend a full session (root-cause probing, building a throwaway repo to test `merge=ours` vs `merge=union` semantics, discovering `merge=ours` isn't a real built-in git driver, wiring a `.gitattributes` policy + `post-rewrite` hook to auto-regenerate dropped generated files) before it could even start draining the 7 stalled PRs. This is exactly the kind of policy `/init-repo` should provision by default for any repo whose CI regenerates tracked docs (STATUS.md-style dashboards, diagrams, changelogs).
- **Proposed enhancement**: `/init-repo` should detect (or let the user declare) "generated-and-committed" doc files regenerated by a pre-commit/post-rewrite hook, and provision a `.gitattributes` merge-driver policy (registering the driver locally, since GitHub's server-side merge ignores `.gitattributes`) plus the regen-after-rebase hook, as a standard repo-config item — not something each repo has to independently discover after accumulating merge debt.
- **Frequency/severity**: seen once as a root-cause investigation, but the underlying condition (STATUS.md/diagrams/progress.md as tracked+regenerated files) recurred across at least 6 of the 18 scanned sessions (see F-OP-02). High cost — burned a full session to fix after the fact.

## F-OP-02 — /merge doesn't anticipate date-sensitive generated-file staleness, forcing a manual regen-and-push cycle before merging
- **Type**: ux-friction
- **Maps to**: merge sub-skill
- **Source**: `64d0f02e-ca63-4585-ae86-4653c3b67bd3.jsonl` (session ~2026-07); same pattern recurs in `6e45c5ad`, `756af4ce`, `9168251d`, `dfe0a3e9`
- **What happened**: Invoking `merge` on PR #1292 hit `BLOCKED`. After digging through CI logs the assistant found: "The taxonomy check itself passed (errors: 0) — the real blocker is a different step: `generate-status.py --check` says `docs/STATUS.md` is stale. That's because #1292 was committed yesterday and STATUS.md carries date-relative content; CI regenerating it today produces a diff." The assistant had to manually regenerate `docs/STATUS.md` on the branch, commit, push, and re-wait for CI before it could merge — extra round trip the merge skill did not anticipate for any PR that has sat open across a day boundary.
- **Proposed enhancement**: Before attempting a merge, the merge sub-skill should proactively regenerate any date-sensitive generated doc on the target branch (or at minimum check-and-warn) rather than discovering staleness only after a `BLOCKED` state and a CI-log dig.
- **Frequency/severity**: recurring — the "STATUS.md is stale" / "regenerate STATUS.md" pattern appears across 6 of the 18 scanned sessions. Medium cost per occurrence (one extra push+CI-wait cycle), but frequent enough to be worth automating.

## F-OP-03 — Append-then-drained doc file (`_intake.md`) excluded from merge driver requires recurring manual, judgment-heavy conflict resolution
- **Type**: missing-capability
- **Maps to**: merge sub-skill / worktree-task-lifecycle
- **Source**: `756af4ce-3aa2-4a20-b912-dc4e59ef94d8.jsonl`; same class of conflict also resolved manually in `55b4f5b5-1488-4838-93fe-ea908b3425a7.jsonl` (PR #1286)
- **What happened**: `docs/learnings/_intake.md` is append-only from the writer's side but periodically drained by a curation PR, so it was deliberately left out of the generated-file merge-driver policy (union would resurrect already-curated entries). Every time a branch that appended to it rebases across a "drain" PR, the conflict must be resolved by hand with real judgment: "this is a conflict where the naive 'keep both' would be wrong... My branch's side of the conflict contains five entries that dev already curated away." This happened at least twice across the scanned sessions, each time requiring a bespoke Python script to surgically diff and resolve rather than a scripted/repeatable procedure.
- **Proposed enhancement**: Document (or better, script) a repeatable resolution procedure for "append-then-periodically-drained" files as a recognized third file class in the merge sub-skill/runbook, alongside "pure regenerate" and "real prose" — e.g. a small helper that diffs the branch's intake additions against what dev's drain PR curated, and keeps only the genuinely new entries automatically.
- **Frequency/severity**: recurring (seen twice, each a multi-step manual resolution); medium cost, high risk (a wrong resolution silently destroys learnings entries — flagged in-session as a near-miss on real data loss in the #1286 case).

## F-OP-04 — /ship not invoked for a batch of finished branches; raw `gh pr create` used instead, leaving the user unsure whether anything was actually merged
- **Type**: trigger-miss
- **Maps to**: ship command / merge command
- **Source**: `6e45c5ad-878f-49c4-986a-61a6d2af3b22.jsonl` (session ~2026-07-15)
- **What happened**: After finishing five work items across six worktrees, the assistant opened all six PRs with raw `gh pr create` calls (confirmed at multiple points in the transcript) rather than invoking the `github` skill's `ship`/`merge` commands. Its closing summary said "All five work items are done and shipped as six PRs against dev, none merged," which read as ambiguous enough that the user replied: "I don't understand, what do you need me to do so that you can merge them all?" The assistant then admitted: "Sorry — I made that sound blockier than it is. Nothing is blocking. I just need your go-ahead to merge."
- **Proposed enhancement**: (1) The `github` skill should trigger whenever the assistant is about to create a PR destined for `dev`/`main`, even mid-flow inside a larger task, not just when the user explicitly types `/ship`. (2) When a batch of PRs is left unmerged pending user go-ahead, the skill's final summary should surface that decision through `AskUserQuestion` (a single batched "merge these N PRs now? Y/N per PR" prompt) instead of prose that can read as informational rather than actionable.
- **Frequency/severity**: seen once as an explicit user-confusion incident, but the underlying pattern (PRs opened via raw `gh` instead of the skill) is the kind of drift likely to recur silently in other sessions without triggering a visible complaint. Medium cost — required an extra clarifying round-trip with the user.
