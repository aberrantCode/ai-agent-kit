Decision Gates · two critical branches
Gate 1: Verification Gate
Attached to Verify phase. Implementation, API, build, security, UI, and code-changing tasks are not final until they have an explicit verification result. Branch condition: if Tests: passing: false is reported, orchestrator creates corrective build/test work and does NOT mark implementation complete. Loop: Execute ← Verify.
Gate 2: Failure Budget
Attached to Execute/Verify boundary. Tolerates up to 5 failures per plan before escalating to user. Each failure adds 1-3 corrective tasks rather than retrying blindly. After 5 failures, plan is paused and detailed issue written to docs/issues/.
Alternate Entry Point · recognized variant
The canonical-repo effort entered Capture directly through docs/requirements/canonical-repo.md, bypassing docs/features/ entirely. This is a recognized alternate entry point, not a deviation. The feature spec phase (Capture → Approve) can be skipped when a requirements document is the source of truth.

Verification Gate · Verify phase branch
If Tests: passing: false
Orchestrator creates corrective build/test work. Implementation task is NOT marked complete. Loop back to Execute phase with new corrective tasks. If a plan already contains a review/quality/test/security/e2e task covering the same CAP-ID, that task satisfies the gate when it succeeds.
Failure Budget · Execute/Verify boundary branch
Up to 5 Failures Allowed
The Error Recovery Loop tolerates up to 5 failures per plan before escalating to user. Each failure adds 1-3 corrective tasks rather than retrying blindly. Tracks cumulative failures per plan.
Escalation at 5+ Failures
After 5 failures, plan is paused and detailed issue is written to docs/issues/. User is notified. Work pauses until user resolves the underlying issue or adjusts scope.
